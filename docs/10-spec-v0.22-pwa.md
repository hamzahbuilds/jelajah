# Spec v0.22 — PWA / Read-only Offline

**Status:** approved by Sage (design nod 6 Sep 2026).
**Scope:** installable PWA + read-only offline. Offline write queueing, push, background sync explicitly OUT (v2 candidates, own specs).

## 1 · Manifest + icons

`public/manifest.webmanifest`: name "Jelajah", short_name "Jelajah", start_url "/", display "standalone", background_color "#F9F9F8", theme_color "#0F766E", icons 192/512 (+ maskable variants). Icons generated by a one-off node script (scripts/make-icons.mjs, uses no deps — draw the pin glyph on a canvas? Node has no canvas without deps — instead: ship a hand-written SVG icon (public/icon.svg, the pin glyph on teal rounded square) and pre-generate PNGs ONCE via Playwright screenshot (dev-only script, playwright already available globally); the PNGs are committed as static assets). `<link rel="manifest">` + `<meta name="theme-color">` in index.html; apple-touch-icon link.

## 2 · Service worker (public/sw.js, hand-rolled, no deps)

Registered from src/main.tsx (`navigator.serviceWorker.register('/sw.js')`, guarded try/catch, production-only via import.meta.env.PROD check).

Strategies (fetch handler, by request class):
- Same-origin GET hashed assets (`/assets/`): cache-first, cache `jl-assets-v<N>`.
- Navigation requests (mode 'navigate'): network-first (3s timeout) → cache fallback of '/' shell; successful network responses update the cache.
- Same-origin GET `/api/` EXCEPT `/api/auth`, `/api/mcp`: network-first → cache fallback (cache `jl-api-v<N>`); when serving fallback, add header `X-Jelajah-Offline: 1` via new Response wrap so the client can detect it.
- GET covers (`/api/trips/*/cover`) and document files: cache-on-fetch, cap cache entries (~40, FIFO trim).
- Everything else (POST/PUT/PATCH/DELETE, cross-origin): pass through untouched — writes NEVER intercepted.

Lifecycle: `install` precaches '/' + manifest + icon; `activate` deletes old-version caches (version bump = editing the `V` constant; the build stamps nothing — bump manually per release note in the file header, or derive from a comment — keep it a manual constant, documented); `skipWaiting` NOT automatic: SW waits, client shows an update toast ("New version — refresh" via the existing toast system listening to `registration.waiting` + controllerchange reload).

Logout: client calls `caches.delete` for the api cache (best-effort try/catch) — mitigation for shared devices, recorded limitation.

## 3 · Client UX

- `src/lib/pwa.ts`: registration, update detection (waiting worker → callback), `clearApiCaches()`.
- Offline banner: fetch-layer detection — api.ts inspects `X-Jelajah-Offline` response header; a tiny context/event sets a slim banner ("Offline — showing last synced data" / BM) shown at top of .main while any recent response was offline-served; clears on next fresh response.
- Update toast wired via existing useToast? Toast auto-dismisses — use a persistent slim banner with a Refresh button instead (same banner component, second variant). EN+BM.

## 4 · e2e

Steps: GET /manifest.webmanifest 200 + name check; sw.js served with correct content-type; (SW registration + offline render: `context.setOffline` after loading plan → reload → plan renders from cache + offline banner visible) — NOTE: wrangler dev serves dist; SW registration requires PROD build — the e2e already runs against `npm run build` output via wrangler, and localhost is a secure context, so registration works; if SW timing proves flaky in CI-like runs, the offline-render step may be downgraded to: assert registration + cache population only, with the ruling recorded.

## 5 · Constraints

RM0/no deps (sw.js + manifest are plain static files; icon PNGs committed); no server/ route changes EXCEPT none needed (assets binding already serves public/ via Vite publicDir — VERIFY public/ lands in dist, tess/ precedent says yes); money untouched; writes never intercepted (spec-level guardrail — reviewer must verify the fetch handler's method check FIRST); t() EN+BM for banner/toast strings; e2e ritual to E2E PASSED v0.22 marker; SW must not break the e2e's other steps (the suite runs in one browser context — if the SW's caching confuses earlier assertions, scope e2e SW steps to a fresh context and/or unregister after).
